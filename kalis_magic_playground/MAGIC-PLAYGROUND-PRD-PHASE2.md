## 0. 작업 전 체크
* **문서 성격**: 본 문서는 kalimagic '마술 놀이터' 커뮤니티의 Phase 1 구현 완료 상태 및 최근 추가 반영된 스펙을 정리하고, 핵심 갭(Gap) 3가지를 도출하여 다음 단계(Phase 2)의 방향성을 정하기 위한 기획 문서(PRD)이다.
* **새 스키마 필요 여부**: 각 후보 기능의 스펙 및 데이터 모델 확장 방향에 따라 신규 테이블 정의 또는 기존 스키마(posts, profiles, qa_answers 등) 변경이 수반될 수 있다.
* **검수 필요성**: 매거진 발행 파이프라인과 같이 외부 공개용 텍스트를 다루거나 편집/각색 프로세스가 개입되는 항목은 `quality-safety-editor` 수준의 검수 절차가 필요하다.

## 1. One-page Brief

### 무엇을 만드는가
Phase 1에서 구축한 '마술 놀이터'의 기본 게시판, Q&A, 모임 후기 연동 및 최근 반영된 뱃지 시스템, 초대 루프, 측정 인프라를 바탕으로, 현재 코드베이스와 원래 기획 사이의 갭(Gap)을 해소하기 위한 Phase 2 후보 기능 3가지를 제시하고 이 중 우선순위를 결정하여 상세 설계를 진행한다.

* **후보 A: 매거진 발행 파이프라인의 완성**
  * 현재 '매거진 후보 지정' 기능까지만 구현되어 있는 상태에서, 실제로 질문을 각색/익명화하여 공식 매거진 카테고리로 최종 발행하는 관리자 도구 및 게시 도선을 구축한다.
* **후보 B: 신고/리포팅 시스템**
  * 커뮤니티 내 유해 게시물이나 스팸을 회원이 직접 신고하고, 관리자가 인박스에서 이를 모더레이션(숨김 처리 등)할 수 있는 안전장치를 신설한다.
* **후보 C: 전문가(Expert) 역할 및 전용 Q&A 활성화**
  * 스키마와 관리자 회원 목록에만 부분적으로 존재하는 'expert' 역할을 공식 정의하고, 전문가만 답변할 수 있거나 전문가가 답변을 남겼을 때 UI 상으로 차별화하는 기능을 활성화한다.

### 왜 만드는가
* **정체성 확립**: "마술이 나를 바꾸고, 내가 남을 바꾸며, 그 반응이 다시 나를 바꾼다"는 칼리의 철학을 커뮤니티에서 실현하기 위해서는 정제된 콘텐츠(매거진) 공급, 안전한 연습 환경 구축(신고/리포팅), 신뢰할 수 있는 피드백(전문가 Q&A)이 필수적이다.
* **측정 기반 의사결정**: 최근 `events`, `invites`, `leads` 테이블을 도입하여 방문, CTA 클릭, 리드 유입 등을 추적할 수 있는 측정 인프라가 확보되었다. 이를 바탕으로 사용자 행동 변화를 정량적으로 관측하며 갭을 채워나갈 시점이다.

### 누구를 위한 것인가
* **커뮤니티 회원**: 안전하고 정제된 환경에서 마술 학습 경로에 대한 해답을 찾고 성장을 경험하려는 학습자들.
* **커뮤니티 관리자 (칼리 및 운영진)**: 유해 게시물을 신속히 제어하고, 유의미한 질문을 매거진으로 발굴/편집하며, 등급 및 역할을 관리하는 모더레이터.

### 성공 기준
* **선행 확인**: 원래 지향했던 '마술 학습 경로 질문 10개 축적'이 실제로 달성됐는지, 신규 구축된 측정(admin-analytics)·인박스 인프라로 지금 처음 실측할 수 있다. 이번 Phase 2 착수 전 이 숫자부터 확인한다.
* **후보 정량 지표**: 선택된 후보 기능별로 무엇을 성공으로 볼지(예: 매거진 발행 건수, 신고 처리 소요시간, 전문가 답변 채택률)는 아직 확정된 목표치가 없다 — 이번 문서의 "7. 승인 대기 질문"에서 칼리형이 정한다.

### 이번 버전에서 하지 않을 것
* 커뮤니티 내 직접 동영상 업로드 기능 (외부 링크 및 기존 연동 유지)
* 결제 모듈 탑재를 통한 유료 멤버십 또는 후원금 자동 연동 (여전히 out of scope)
* 실시간 채팅 및 1:1 DM (Direct Message) 기능 개발

## 2. PRD

### 목적
Phase 1 배포 이후 실제 추가된 변경사항들과의 정합성을 확보하고, 핵심 기능적 공백을 선택적으로 해결하여 '마술 놀이터'를 신뢰할 수 있는 양질의 지식 아카이브로 진화시킨다.

### 제품 원칙
1. **신뢰와 안전**: 나이와 서열에 무관하게 누구나 안전하게 마술을 연습하고 질문할 수 있는 환경을 보장한다.
2. **점진적 구전**: 억지스러운 가입 유도 대신 초대 루프와 양질의 아카이빙 콘텐츠를 통해 자연스러운 유입을 지향한다.
3. **인프라 기반 검증**: 주관적 감각에 의존하지 않고 로그와 유입 funnel을 측정하여 기능을 고도화한다.

### 핵심 사용자
* **입문자 (Newbie)**: 마술 학습 경로를 질문하고, 선배들의 정제된 매거진을 읽으며 학습 방향을 잡는 사용자.
* **관리자 (칼리)**: 유해 글을 관리하고, 우수 질문을 매거진으로 가공하며, 적절한 등급과 뱃지를 부여하는 주체.

### MVP 기능

#### [후보 A] 매거진 발행 파이프라인
* **기능 요약**: 기존 `admin-moderate`에 있는 '매거진 후보 지정(`magazine_candidate=true`)' 단계를 넘어서, 관리자가 후보 목록을 조회한 뒤 이를 편집(익명 가공, 오탈자 교정 등)하여 정식 매거진으로 등록하는 흐름을 완성한다.
* **검토 배경**: 현재 코드상에는 후보 지정 플래그만 있고, 실제 발행을 위한 에디터 및 변환 로직이 누락되어 있다. 가장 공백이 작고 구현이 빠른 기능이다.
* **미확정 사항**: 원본 글을 유지한 채 새로운 매거진 레코드를 생성할 것인지, 아니면 기존 레코드의 카테고리를 'magazine'으로 전환하며 내용을 덮어쓸 것인지에 대한 정의가 필요하다.

#### [후보 B] 신고 / 리포팅 시스템
* **기능 요약**: 일반 사용자가 부적절한 게시물이나 댓글을 발견했을 때 '신고'할 수 있는 버튼을 제공하고, 신고 데이터가 쌓이면 관리자 인박스에 경고 알림이 표시되며, 즉각 숨김 처리할 수 있는 기능을 제공한다.
* **검토 배경**: 현재 넷리파이 서버리스 함수나 데이터베이스 내에 신고 관련 엔드포인트가 전무한 상태이다. 서비스 규모 확장 시 안전성 확보를 위해 선행되어야 할 기능이다.
* **미확정 사항**: 신고 누적 횟수에 따른 자동 숨김 처리를 도입할 것인지, 아니면 관리자 확인 후 수동 처리만 지원할 것인지의 세부 정책이 미정이다.

#### [후보 C] 전문가(Expert) 역할 활성화
* **기능 요약**: `profiles` 테이블의 역할(role) 체계 중 `expert`를 실제로 활성화하여, 질문 작성 시 '전문가에게만 공개'하는 필터를 UI 상에 노출하고, 전문가 권한을 가진 유저가 답변 시 전용 표식(인증 마크)을 출력한다.
* **검토 배경**: 데이터베이스 및 관리자 관리 UI의 흔적으로는 기획되어 있으나, 구체적인 권한 작동 로직 및 전문가 지정 기준이 부재하여 활성화되지 않은 채 잠겨 있다.
* **미확정 사항**: 전문가를 지정하는 기준(칼리의 수동 임명 방식 vs 특정 퀘스트 뱃지 획득 시 자동 승격 등)과 전문가 답변에 대한 가치 부여 정책이 확정되지 않았다.

### 비요구사항
* 사용자가 직접 커뮤니티에 대용량 비디오 파일을 업로드하여 재생하는 인프라 구축 (유튜브/비메오 등 외부 링크 임베드 유지).
* 실시간 채팅 및 알림 푸시 (사용자가 직접 방문하여 확인하는 비동기식 커뮤니티 모델 유지).
* 후원 뱃지 등의 수동 부여를 넘어선 PG사 결제 자동화 연동.

### 위험 요소
* **개인정보 및 저작권 침해**: 매거진 발행 시 질문자의 동의 없이 글을 노출하거나 익명화가 불충분할 경우 작성자의 반발을 살 수 있음.
* **모더레이션 부하**: 신고 시스템이 남용되거나 어뷰징 수단으로 쓰일 경우, 소수의 관리자(칼리)가 수많은 신고 건을 일일이 확인해야 하는 운영 병목 발생.
* **전문가 신뢰성 저하**: 전문가 등급의 기준이 모호할 경우 답변의 공신력이 떨어지고 일반 커뮤니티 회원 간의 위화감을 조성할 우려가 있음.

## 4. Design Doc / Tech Spec

### 1) 매거진 발행 파이프라인 관련 스키마 확장 (후보 A 선택 시)
* `posts` 테이블에 `is_magazine` (boolean, default false), `original_post_id` (foreign key, nullable) 컬럼 추가 검토.
* 발행 시 원본 글의 소유권을 `system` 혹은 `kalimagic` 공식 계정으로 변경하여 저장하거나, 원본 질문의 작성자 정보를 완전히 비식별화하는 로직 구현.

### 2) 신고 테이블 정의 (후보 B 선택 시)
기존 마이그레이션 컨벤션(uuid 기본키, RLS enable + 정책 0개, service client 전용 접근)을 그대로 따른다.
```sql
create table if not exists public.post_reports (
  id uuid primary key default gen_random_uuid(),
  post_id uuid not null references public.posts(id) on delete cascade,
  reporter_user_id uuid null references auth.users(id) on delete set null,
  reason text not null check (char_length(reason) between 1 and 300),
  created_at timestamptz not null default now()
);
alter table public.post_reports enable row level security;
-- 정책 없음: service client(Netlify Functions)만 접근.
```
* `admin-moderate` API에 신고 건수 조회 및 필터링 기능 추가(신고 누적순 정렬 등).

### 3) 전문가 역할 활성화 (후보 C 선택 시)
* `profiles.role` 제약 조건에 `'expert'`가 정상 포함되어 있는지 확인 및 조정.
* `qa_answers` 조회 시 `profiles` 테이블과 JOIN하여 작성자의 `role`이 `'expert'`인 경우 UI에서 뱃지 표시 로직 삽입.

## 5. Migration / Rollback Plan

### 마이그레이션 계획
* **스키마 변경**: Supabase/PostgreSQL 마이그레이션 SQL 작성 후 개발계 선적용 및 검증.
* **데이터 전환**:
  * 매거진 파이프라인의 경우, 기존에 `[매거진]` 말머리를 달고 수동 작성된 posts 레코드를 신규 규칙에 맞게 마이그레이션하는 스크립트 실행.
  * 전문가 역할의 경우, 지정 대상 유저의 `profiles.role` 값을 `'expert'`로 업데이트하는 쿼리 실행.

### 롤백 계획
* 신규 컬럼/테이블을 추가하는 마이그레이션이므로, 문제 발생 시 새롭게 추가된 API 엔드포인트를 닫고 이전 UI 코드로 롤백 배포를 수행한다. DB 스키마 롤백은 `DROP TABLE` 또는 `ALTER TABLE DROP COLUMN` 스크립트를 준비하여 대응한다.

## 7. 승인 대기 질문

1. **우선순위 결정**: 오늘 제시된 세 가지 후보(A. 매거진 발행 파이프라인 완성, B. 신고/리포팅 시스템 구축, C. 전문가 역할 활성화) 중 이번 Phase 2에서 **가장 먼저 해결해야 할 핵심 과제**는 무엇이라고 보십니까?
2. **매거진 발행 정책**: 매거진 발행을 진행할 때, **원본 질문 글을 원상태로 남겨둔 채 편집된 사본을 매거진 카테고리에 새로 등록**하는 방식이 좋겠습니까, 아니면 **원본 질문 자체를 가공하여 카테고리만 매거진으로 전환**하는 방식이 좋겠습니까?
